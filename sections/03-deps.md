**Генератор задач на разрешение зависимостей пакетов**

Задача разрешения зависимостей пакетов решается менеджерами пакетов и заключается в определении, какие версии прямых и транзитивных зависимостей пакета следует установить. Задача разрешения зависимостей является NP-полной [@vouillon2013] и может быть сведена к задаче выполнимости булевой формулы (Boolean Satisfiability Problem, SAT) [@nieuwenhuis2006]. Для решения SAT могут использоваться решатели NP-полных задач, такие как, например, Z3 [@demoura2008] и MiniZinc [@nethercote2007]. Расширением SAT является задача выполнимости формул в теориях (Satisfiability Modulo Theories, SMT) – в SMT, в отличие от SAT, формула может включать предикаты, оперирующие битовыми векторами.

В задачах, автоматически созданных генератором задач на разрешение зависимостей пакетов, студентам предлагается решить задачу разрешения зависимостей для случайно сгенерированного графа зависимостей. Пример автоматически созданной генератором задачи показан на @fig:deps. Решение задачи принимается только в том случае, если студентом были правильно указаны версии для каждого из перечисленных в задаче пакетов. В каждой сгенерированной задаче студентам предлагается проанализировать случайный граф зависимостей, пример которого показан на @fig:deps, и для каждого пакета в графе зависимостей выбрать его версию, которую следует установить, либо явно указать, что пакет устанавливать не следует. Выбирать версии пакетов следует таким образом, чтобы при их установке не возникало конфликтов версий.

![Сгенерированный граф зависимостей](./images/fig2.png){#fig:deps width=6.3in}

В графе, показанном на @fig:deps, зависимости необходимо разрешить для пакета app версии 1.0.0, корректно указав версии пакетов monaco-editor, `@replit/codemirror-css-color-picker`, lodash, react. Пометки, сделанные на @fig:deps зелёным и красным цветом, студент при решении задачи не видит. Зелёным цветом на @fig:deps выделены версии зависимостей, являющиеся решением задачи. Красным цветом выделены версии пакетов, не являющиеся решением, поскольку их выбор приводит к конфликту версий – при установке monaco-editor версии 2.3.0 требуется также установить пакет `@replit/codemirror-css-color-picker` версии 3.3.0, зависящий от lodash версии 2.5.0, при этом monaco-editor зависит от lodash версии 2.6.0.

Разработанный генератор задач на разрешение зависимостей пакетов основан на программировании в ограничениях [@shcherbina2011; @narinyani1998], в процессе генерации используется метод «сгенерировать и проверить» (generate and test) [@sovietov2021]. Архитектура этого генератора задач показана на @fig:arch.

![Архитектура генератора задач](./images/fig3.png){#fig:arch width=6.3in}

Как показано на @fig:arch, на первом шаге генерируется случайный направленный ациклический граф (Directed Acyclic Graph, DAG) зависимостей. Сгенерированный граф зависимостей транслируется в SMT-формулу, которая затем проверяется на наличие решений. В случае, если решения не были найдены, сгенерированный граф отклоняется и генерируется новый граф. В случае, если найденное решение не является единственным, сгенерированный граф также отклоняется. В противном случае граф принимается и транслируется во внешнее представление для загрузки в систему управления обучением.

Алгоритм генерации случайного графа зависимостей показан на @fig:dag.

![Алгоритм генерации случайного графа зависимостей](./images/fig4.png){#fig:dag width=5.4in}

При инициализации алгоритма, показанного на @fig:dag, в граф $G$ добавляется корневая вершина $n_{\mathrm{root}}$, в соответствие которой ставится пустое множество смежных с ней вершин (строки 2--4). Это множество заполняется в процессе работы алгоритма. Вершины в графе $G$ представлены парами, состоящими из номера пакета и версии пакета, корневой пакет имеет номер 0 и версию 0 (строка 1). После инициализации алгоритма функция $\mathrm{rand}$ генерирует случайное целое из промежутка $[d_{\min}, d_{\max}]$ – так определяется глубина генерируемого графа (строка 5).

Генерация вершин на ярусе $p$ начинается с копирования графа $G$ (строка 6), после чего определяется ширина яруса $p$ – функция $\mathrm{rand}$ генерирует случайное целое из промежутка $[w_{\min}, w_{\max}]$ (строка 7). На каждой итерации цикла (строки 7--12) в граф $G$ добавляется вершина $n_{v}$, в соответствие которой ставится пустое множество смежных с ней вершин (строка 9). Номером пакета, связанного с вершиной $n_{v}$, считается номер яруса $p$, а номером версии пакета считается номер вершины $v$, расположенной на ярусе $p$ (строка 8). Затем случайным образом выбранные вершины из копии графа $G^{*}$, помещённые в множество $A$, соединяются с вершиной $n_{v}$ (строки 10--12) путём добавления вершины $n_{v}$ в множество $G[n]$, содержащее вершины, смежные с $n$ (строки 11--12). Число соединяемых с $n_{v}$ вершин графа также генерируется случайно функцией $\mathrm{rand}$ из промежутка $[k_{\min}, k_{\max}]$ (строка 10). Результатом работы алгоритма является граф $G$ и корневая вершина $n_{\mathrm{root}}$.

Значения минимальной и максимальной глубины графа $d_{\min}$ и $d_{\max}$, значения минимальной и максимальной ширины яруса $w_{\min}$ и $w_{\max}$, значения минимального и максимального числа ссылок на пакет $k_{\min}$ и $k_{\max}$ являются гиперпараметрами алгоритма, которые определяют желаемую сложность задачи. В курсе Конфигурационного управления РТУ МИРЭА используются следующие значения параметров: $d_{\min} = 4$, $d_{\max} = 5$, $w_{\min} = 2$, $w_{\max} = 3$, $k_{\min} = 1$, $k_{\max} = 2$.

Алгоритм, показанный на @fig:dag, не обязательно генерирует такие графы, для которых задача разрешения зависимостей имеет решение. Для обеспечения возможности автоматической проверки решения задачи в некоторых системах управления обучением необходимо добиться того, чтобы решение задачи существовало и при этом было единственным. В связи с этим для оценки пригодности сгенерированного графа зависимостей для автоматической проверки используется алгоритм, показанный на @fig:solve.

![Алгоритм проверки единственности решения](./images/fig5.png){#fig:solve width=5.2in}

Работа алгоритма проверки единственности решения, показанного на @fig:solve, начинается с посещения каждой вершины $n$ графа $G$ (строка 2). Смежные с $n$ вершины $G[n]$ группируются функцией $\mathrm{group\_versions}$ по номеру пакета так, что каждая группа представлена множеством, содержащим все совместимые с пакетом $n$ версии одного и того же пакета. После этого для каждой группы создаётся SMT-ограничение с использованием оператора импликации, задающего правило «если устанавливается пакет $n$, то необходимо установить одну из версий пакета $g$» (строки 3--4). Затем вершины графа $G$ группируются по номеру пакета и для каждого пакета создаётся новое SMT-ограничение, задающее правило «для каждого пакета $g$ может быть установлена только одна из его версий $n_{g}$» (строки 5--6). Также добавляется SMT-ограничение, предписывающее обязательно установить корневой пакет $n_{\mathrm{root}}$ (строка 7).

На следующем шаге алгоритма на @fig:solve выполняется проверка, что полученная из графа зависимостей $G$ SMT-формула имеет решения (строка 8). Если решение существует, то оно представлено множеством $S$ вершин графа $G$, соответствующих выбранным версиям пакетов, которые следует установить. Для проверки, что найденное решение является единственным, создаётся новое SMT-ограничение, исключающее из SMT-формулы все пакеты, принадлежащие множеству $S$, содержащему пакеты, являющиеся решением задачи (строки 9--10). В случае, если дополненная таким образом SMT-формула не имеет решений, сгенерированный граф зависимостей считается имеющим единственное решение и, следовательно, пригодным для автоматической проверки (строки 11--12).

Пригодный для автоматической проверки граф зависимостей, сгенерированный по показанному на @fig:dag алгоритму, а также множество $S$, содержащее решение задачи разрешения зависимостей, вычисленное по показанному на @fig:solve алгоритму, подаётся на вход транслятору внутреннего представления задачи во внешнее представление. Для визуализации графа зависимостей используется инструмент graphviz [@ellson2004]. Например, для создания тестовых задач в системе Moodle [@gamage2022] внутреннее представление транслируется в формат GIFT, который может быть импортирован в систему управления обучением встроенными в Moodle средствами.

Пример пользовательского интерфейса Moodle показан на @fig:moodle.

![Задача разрешения зависимостей в пользовательском интерфейсе системы Moodle](./images/fig6.png){#fig:moodle width=6.3in}

Как показано на @fig:moodle, на этапе трансляции графа зависимостей в формат GIFT для системы Moodle номера пакетов заменяются на их имена, а номера версий пакетов переводятся в формат SemVer. Задача разрешения зависимостей пакетов при этом считается решённой только в том случае, если правильно указаны версии для каждого из пакетов в графе.
